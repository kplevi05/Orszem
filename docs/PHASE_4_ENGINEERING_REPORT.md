**Status:** implementation, tests and CI complete; **not** deployed; Phase 5 not started.

## A. What was built

The first thing Őrszem actually exists for: an anonymous citizen can submit a railway
safety/security report and later check its status, without an account, a password, or
anything that identifies them. Concretely:

- The frozen V2 event taxonomy (`report_categories` / `report_event_types`), seeded once by
  migration and served through a Public catalogue endpoint.
- Anonymous report creation (`POST /api/v1/public/reports`) with strict input validation,
  client-driven idempotency, and a routing decision captured atomically with the report.
- Public report lookup (`GET /api/v1/public/reports/{publicReportId}`), gated by a
  client-generated access credential, with existence-safe (indistinguishable) failures.
- Caddy access-log redaction for the new credential header, verified end to end.

Explicitly **not** built, per the phase brief: any client UI, the Service workflow/report
API, moderation, analytics, rate limiting (§L), retention/expiry, and anything from Phase 5.

## C. Schema (V003, additive only)

`report_categories` / `report_event_types` — the taxonomy, `code` stable once published,
deactivated (never deleted) when retired. Seeded from `docs/product/EVENT_CATALOG_V2.md`,
verified programmatically before the migration was written and again by
`EventCatalogSchemaIT`: **exactly 7 categories, 61 event types**, unique codes shaped
`^[A-Z][A-Z0-9_]*$`, `display_order` unique globally for categories and per-category for
event types.

`reports` — `id` (internal, never exposed) / `public_id` (the only identity a client gets,
unique) / `client_submission_id` (unique — the idempotency key) /
`public_access_credential_hash` (`BYTEA`, `CHECK octet_length = 32`) / `occurred_at` /
`submitted_at` / `train_identifier` (optional, `CHECK` trimmed and ≤ 64 chars) /
`settlement_id` (FK) / `submitted_railway_line_id` (FK, optional — the raw client
selection, not the routing decision) / `event_type_code` (FK) / `status`
(`NEW`/`IN_PROGRESS`/`ARCHIVED`, `CHECK`).

`report_routing_snapshots` — one row per report, **current state, not history** (ADR 0008
Decision 5). `CHECK` enforces: `ROUTED` always names a service area and a resolved line and
carries no reason; `UNCLASSIFIED` always carries a reason and never a service area (its
resolved line is unconstrained — present for the three reasons reached only after a line
resolved, absent for the three reached before one ever did).

A report's own FKs (`settlement_id`, `submitted_railway_line_id`, `event_type_code`)
deliberately do **not** require `active = true` at the database level — a historical report
referencing something since deactivated must keep resolving; only submission-time
validation cares about `active`.

## D. Taxonomy validation

Verified three independent ways: (1) a generator script parsed
`docs/product/EVENT_CATALOG_V2.md` and confirmed 7/61, unique codes, and deterministic
ordering *before* the migration SQL was written, to avoid transcription errors; (2)
`EventCatalogSchemaIT` re-asserts the same facts against the real, applied migration; (3)
the same test asserts the Public catalogue endpoint's content and ordering match the
database exactly, and that deactivating one category or event type removes it from the
catalogue without deleting the row.

## E. Credential design (ADR 0008 Decision 1)

`PublicReportAccessCredential` — `pr_` + 43 URL-safe base64 characters, the unpadded
encoding of exactly 256 CSPRNG-random bits. **Generated by the client, never the backend** —
the backend validates shape only and stores `SHA-256(credential)`, never the credential
itself and never a reversible or HMAC-based form. Sent as `X-Orszem-Report-Access` on every
request that needs it, never a query parameter, path segment, cookie, or response body.
Verified with `MessageDigest.isEqual` (JDK-documented constant-time in the compared
lengths) — deliberately not Argon2, since the credential already carries uniform 256-bit
entropy by construction, unlike a human-chosen password.

Because the client generates it *before* the first submission attempt, a lost response
after a committed database write is always safely retryable: the client already has
everything (`clientSubmissionId` + credential) needed to retry, and the backend never needs
an idempotency-response cache or a way to answer "what was my credential again" — a
question it must never be able to answer.

## F. Idempotency semantics (ADR 0008 Decision 2)

`clientSubmissionId` is the idempotency key, enforced as a database `UNIQUE` index, not an
application check-then-insert. A replay is recognised by comparing **normalized business
fields** (`occurredAt` as an `Instant`, normalized `trainIdentifier`, `settlementId`,
optional `railwayLineId`, `eventTypeCode`) — never a hash of the raw request — so JSON
whitespace, property order, and equivalent textual timestamp representations never change
the outcome (`PublicReportIdempotencyIT` proves all three explicitly).

**Ordering is load-bearing and tested**: a replay is recognised and answered from what is
already stored *before* any business validation runs against today's state. A settlement
active on day 1 and deactivated by a day-30 retry still returns the original report — never
a fresh `INVALID_SETTLEMENT` computed against now-stale state. The same holds even if the
reference dataset itself becomes entirely unavailable between the original submission and
the retry.

Same id, matching payload and credential → the same report, replayed (HTTP 200). Same id,
differing payload *or* credential → `IDEMPOTENCY_KEY_REUSED` (HTTP 409) — deliberately one
code for both kinds of mismatch, so a caller cannot use the response to infer which part of
a guessed request was closer to the original.

## G. Routing behaviour (ADR 0008 Decision 4)

Once `settlementId`/`eventTypeCode` (and, if supplied, `railwayLineId`) are validated to
exist — and, for settlement/event type, to be active — **every** `RoutingService` outcome
results in a successfully created report: `Routed` and all six `Unclassified` reasons
alike, `REFERENCE_MISMATCH` included. A known railway line with no verified relation to the
settlement is not proof the reporter is wrong; refusing the report on that basis would
silently discard a genuine safety report over a data-completeness gap. `PublicReportSubmissionIT`
exercises all seven outcomes explicitly and asserts each persists the correct snapshot.

Only two conditions refuse the request before a report is ever created:
`INVALID_SETTLEMENT` / `INVALID_EVENT_TYPE` / `INVALID_RAILWAY_LINE` (the identity itself
does not resolve, or is not active), and `REFERENCE_DATASET_UNAVAILABLE` (no current
reference state exists to route against at all — infrastructure, not a business result,
per ADR 0007).

**Locking:** a submission holds `ReferenceStateLock` **shared** (`pg_advisory_xact_lock_shared`,
new this phase) for its whole transaction while it reads reference/service-area state and
routes; a reference import holds the same key **exclusive** (unchanged from Phase 3B/3C).
Many submissions run concurrently without contending with each other; an import waits for
every in-flight submission to finish, and a submission that begins mid-import waits for the
import to finish first — so a submission's view of reference state is always one consistent
revision, never a half-applied mix. `PublicReportConcurrencyIT`'s third test proves this
against real PostgreSQL, not by inspection (§I).

## H. API contract

| Endpoint | Method | Auth | Notes |
|---|---|---|---|
| `/api/v1/public/report-catalog` | GET | none | active categories + event types, nested, ordered |
| `/api/v1/public/reports` | POST | `X-Orszem-Report-Access` (required) | 201 created / 200 replayed |
| `/api/v1/public/reports/{publicReportId}` | GET | `X-Orszem-Report-Access` (required) | 200 / 404 |

Submission body: `clientSubmissionId`, `occurredAt`, `trainIdentifier?`, `settlementId`,
`railwayLineId?`, `eventTypeCode`. **No `categoryCode`** — derived server-side from
`eventTypeCode` alone. No free text, no coordinates, no media. An unrecognised body field
is rejected (400 `VALIDATION_ERROR`), not silently discarded — see §J.

Submission response: `reportId` (the public id), `submittedAt`, `initialStatus` (always the
literal `"RECEIVED"` — every report Phase 4 creates is `NEW`, which always maps there).
Never the credential, never the internal id, never the routing decision. `201` carries a
`Location` header; both `201` and `200` carry `Cache-Control: no-store`.

Lookup response: `reportId`, `occurredAt`, `submittedAt`, `trainIdentifier`, `settlement
{id, name}`, `category {code, displayName}`, `eventType {code, displayName}`, `status`
(the Public vocabulary: `RECEIVED`/`PROCESSING`/`CLOSED` — `NEW` is never sent, by name or
by inference). `no-store` on every response, success or failure.

Stable error codes added: `INVALID_REPORT_ACCESS_CREDENTIAL`, `INVALID_EVENT_TYPE`,
`INVALID_SETTLEMENT`, `INVALID_RAILWAY_LINE`, `IDEMPOTENCY_KEY_REUSED`, `REPORT_NOT_FOUND`
— documented in OpenAPI (`/v3/api-docs`) alongside the 404/409/503 responses and the custom
header, all asserted by `PublicReportSerializationIT`.

## J. Concurrency proof (§45, §I)

All three required races run as real concurrent HTTP requests (or, for the third, a real
raw-JDBC transaction) against the live server, not simulated:

1. **N (8) identical concurrent submissions**, same id/payload/credential → exactly one
   `201`, the rest `200` replays, all naming the same report; exactly one database row.
2. **N (8) concurrent submissions sharing an id but disagreeing on payload** → exactly one
   `201`; every other request `409 IDEMPOTENCY_KEY_REUSED`; exactly one database row.
3. **A submission racing an in-flight reference import**: a background thread holds the
   real exclusive advisory lock (`pg_advisory_xact_lock` on `ReferenceStateLock.KEY`, the
   same mechanism a real import uses) in an open, uncommitted transaction; a concurrent
   submission is proven to genuinely block (it must not complete within 800 ms while the
   lock is held); once the import commits new reference data and releases the lock, the
   submission completes and its persisted routing snapshot is asserted to reflect the
   import's **finished** state (`ROUTED` via the newly-imported line), never the pre-import
   or a half-applied state.

No `synchronized`, no in-memory mutex, no Redis anywhere in this — the database's own
unique index and advisory-lock semantics are what make all three true.

## K. Security review

- Credential never logged, never returned, never stored except as its SHA-256; compared
  constant-time. Caddy access logs redact `X-Orszem-Report-Access` (custom header, no
  built-in protection) — verified with a real request and a negative control
  (`scripts/verify-caddy-header-redaction.sh`); `Authorization` is also pinned explicitly
  even though Caddy 2.11.4 already redacts it unconditionally by default (confirmed by
  testing, not assumed — no negative control is possible for it for that reason).
- `PublicReportLookupIT` proves unknown id / missing / malformed / wrong credential are
  byte-identical 404s, and that a Service bearer token and a report access credential
  cannot be used in place of each other in either direction.
- **Jackson finding, corrected during implementation:** this Jackson 3 version's default is
  globally lenient about unknown JSON properties, and a per-class
  `@JsonIgnoreProperties(ignoreUnknown = false)` does **not** override that default here —
  confirmed empirically with an isolated probe before shipping a fix, not assumed from
  Jackson 2 behaviour. Flipping the global setting was rejected (it would affect every
  other endpoint, which the brief explicitly forbade); instead `SubmitReportBodyAdvice`
  (`RequestBodyAdvice`) checks the raw JSON's top-level field names against exactly what
  `SubmitReportRequest` declares, scoped to that one endpoint, before Spring's normal
  (still globally-lenient) conversion runs.
- **CI-only findings, not present locally:** the verification script initially failed in CI
  twice, for two unrelated reasons — a Caddy admin-port collision with the pre-existing
  `verify-caddy-routing.sh` step sharing the same runner, and a missing executable bit on
  the new script file (git recorded it as `100644`, not `100755`). Both fixed and reverified
  green; see §B.
- No SQL string concatenation anywhere in the new repositories — every value is bound.
- `/api/v1/service/**` remains untouched and still requires authentication; `/api/v1/public/**`
  is the only surface widened, exactly as intended (`SecurityConfig` unchanged in substance).
- No audit event is written for an anonymous submission (ADR 0008 Decision 7) — the report
  row is its own authoritative record; writing a high-volume, unattributable copy into the
  security audit trail would blur what that trail is for.

## L. Known limitations

- **No rate limiting or abuse defence exists for `POST /api/v1/public/reports`.** This is
  the single most important limitation of this phase and is not deployed publicly as a
  result. See `DECISIONS_REQUIRING_OWNER.md` B6 for why `LoginRateLimiter` was not reused
  (different traffic shape, would require inventing an unjustified threshold) and what a
  concrete answer needs to cover.
- No retention policy, deletion, or credential expiry (`DECISIONS_REQUIRING_OWNER.md` B5) —
  a report and its access credential remain valid indefinitely. Deliberate non-decision,
  not an oversight.
- `trainIdentifier` has no catalogue or timetable validation — a bounded, unvalidated
  string (`DECISIONS_REQUIRING_OWNER.md` B3, still open).
- No moderation workflow exists; `reports.status` is `NEW` for every report Phase 4 creates,
  by construction (`DECISIONS_REQUIRING_OWNER.md` B7, still open).
- `report_routing_snapshots` is current-state-only, not history — a future re-routing phase
  overwrites it with no audit trail of the prior value (ADR 0008 Decision 5, by design).
