# V2 disaster recovery

Companion to `docs/OPERATIONS_RUNBOOK.md`. That document covers routine operations; this
one covers "something is gone" - what is reconstructable from Git alone, what requires a
backup, what requires an owner-held secret, and the order to restore things in.

No secret value appears anywhere in this document.

## Recovery source of truth, by category

| Category | Source of recovery | Notes |
|---|---|---|
| Application code (backend, Android, Web) | Git (GitHub) | Any commit can be rebuilt from source; nothing here is a single point of failure. |
| Deployment configuration (Caddyfile, systemd unit, env **template**) | Git | The *filled-in* `/etc/orszem/backend.env` is not in Git (§6/§34 of the Phase 14 brief) - see "Secrets" below. |
| Business data (users, reports, moderation, audit, routing, reference-data import state) | The most recent verified PostgreSQL backup | Nothing else reconstructs this. A day with no verified backup is a day of data that cannot be recovered if the VM is lost. |
| Reference dataset **content** (settlements/railway lines as CSV) | `reference-data/` in Git | The canonical source. What matters after a restore is that the *imported, DB-resident* state matches what the backup captured - re-importing a newer canonical dataset is a separate, deliberate operation, never an automatic part of restore (§25). |
| Android/production signing key | Owner-held, off-repository | Never in Git, never generated by CI (§38/§66). If lost, the only path forward for existing installs is publishing a new app identity - there is no recovery. |
| TLS certificates | Caddy's automatic HTTPS, re-acquired | Not a backup concern - see "Re-creatable vs critical state" below. |

## Re-creatable infrastructure state vs. critical business data

This distinction matters because it is easy to over-scope a disaster-recovery plan into
backing up things that do not need it:

- **Critical (must come from a backup):** everything in the PostgreSQL database. There is
  exactly one source of truth for it and it is not derivable from anything else.
- **Re-creatable (does not need its own backup):** Caddy's ACME certificate state. If lost,
  Caddy re-acquires a certificate automatically the next time it starts, provided DNS still
  resolves to the host and ports 80/443 are reachable - that is the entire point of
  automatic HTTPS. Losing it is an availability blip during re-acquisition, not a data-loss
  event, and is not listed as a backup requirement.
- **Re-creatable (build artifact, not data):** the backend jar and the Public Web `dist/`
  bundle. Both are deterministic outputs of a Git commit plus the documented build steps
  (§8/§39/§41) - keep the *commit SHA* recorded (see `OPERATIONS_RUNBOOK.md` §4), not the
  artifact itself, as the thing that must survive.

## Scenario playbook

For each scenario: what is reconstructable from Git, what requires the backup, what
requires an owner-held secret, and the restore order.

### 1. Backend application lost (process/binary gone, VM and DB intact)

- From Git: rebuild the backend jar from the recorded commit SHA (`OPERATIONS_RUNBOOK.md`
  §4), or restore the last known-good jar if it was retained.
- Backup needed: no - the database was never touched.
- Owner secret needed: no.
- Order: reinstall the jar per `SERVER_RUNBOOK.md` §6, `systemctl start orszem-backend`,
  confirm `/actuator/health`.

### 2. Public Web artifact lost (`dist/` gone, everything else intact)

- From Git: `npm ci && npm run build` from the recorded commit SHA, `rsync` the output back
  into place per `SERVER_RUNBOOK.md` §4.
- Backup needed: no.
- Owner secret needed: no.

### 3. PostgreSQL process/container lost, but the data volume/path is intact

- From Git: nothing needed - this is a service restart, not data loss.
- Backup needed: no, provided the data directory is genuinely intact. Confirm with
  `sudo systemctl start postgresql && sudo -u postgres psql -c '\l'` before assuming so.
- Owner secret needed: no.
- Order: restart PostgreSQL, confirm it is reachable on loopback only, restart the backend
  (it will fail its own DB connectivity check loudly if the assumption above was wrong -
  see `OPERATIONS_RUNBOOK.md` §13).

### 4. PostgreSQL data volume/path lost

- From Git: the empty schema (all Flyway migrations) - reconstructable, but contains none
  of the actual data.
- Backup needed: **yes, this is the scenario backups exist for.** Restore the most recent
  verified `.dump` per `OPERATIONS_RUNBOOK.md` §6.
- Owner secret needed: only the database credentials already in `/etc/orszem/backend.env`
  (unaffected by this scenario if the host filesystem outside the PostgreSQL data
  directory is otherwise intact).
- Data loss: everything written after the backup's snapshot moment - this is the
  documented RPO, see §AC below.
- Order: create a fresh, empty `orszem_v2` database/role (`SERVER_RUNBOOK.md` §2),
  restore, start the backend, run the full verification checklist
  (`OPERATIONS_RUNBOOK.md` §9).

### 5. Whole VM lost

This is scenarios 1-4 combined, plus infrastructure that was never a backup concern in the
first place (the OS, Caddy's TLS state) needing to be recreated from scratch on a new host.

- From Git: application code, deployment config, reference-data CSVs, migrations - all of
  it.
- Backup needed: **yes, and it must be an off-host copy.** If the only copy of the most
  recent `.dump` lived on the lost VM, it is gone too - see `OPERATIONS_RUNBOOK.md` §5
  "Backup destination". **This repository does not claim recovery from a whole-VM loss is
  possible unless a verified off-host backup copy exists** - that is an explicit owner
  decision (destination not yet selected; see the known limitations in the Phase 14
  engineering report), not an automatic guarantee of this document.
- Owner secret needed: **yes** - the Android release signing key (owner-held, off-repo, no
  recovery path if lost - see §38/§66 of the brief), fresh database credentials (generated
  new, never reused from the lost VM per policy), and DNS access to point the A records at
  the new host's IP.
- Order:
  1. Provision a new host, re-run `SERVER_RUNBOOK.md` end to end on it (new IP);
  2. restore the most recent off-host backup (scenario 4);
  3. redeploy the application and Public Web (scenarios 1-2);
  4. re-point DNS at the new host's IP - **owner-gated** (`PRODUCTION_DNS_CUTOVER_APPROVED`
     in the Phase 14 engineering report's gate table);
  5. let Caddy re-acquire certificates automatically;
  6. run the full post-deployment smoke checklist (`OPERATIONS_RUNBOOK.md` §15).

### 6. Latest backup corrupted

- `scripts/orszem-restore.sh` refuses a corrupted archive, a mismatched checksum, and a
  non-empty target database before touching anything (all three verified by automated
  negative tests in `scripts/orszem-restore-drill.sh` - see Phase 14 engineering report
  §M) - this scenario is caught, not silently made worse.
- Fall back to the next-most-recent verified backup. This is the practical argument for
  the retention proposal in `OPERATIONS_RUNBOOK.md` (daily/weekly/monthly, owner review
  pending) rather than keeping only the single latest copy.
- Data loss: whatever was written between the good backup and the corrupted one's
  intended snapshot point, in addition to the normal RPO.

### 7. Signing machine lost

- The V2 Android release signing key is owner-held, generated on a secure owner-controlled
  machine, and explicitly never stored in this repository or in CI (§38/§66). If the
  machine holding it (and its backup copy - see the owner-gate `V2_RELEASE_SIGNING_KEY_READY`
  in the engineering report) is lost with no other copy, **there is no recovery**: existing
  installs cannot receive a signed update under the same application identity. This is
  stated plainly rather than implying a recovery path that does not exist.
- This repository's only responsibility here is to never hold a copy that could have been
  lost together with the machine, and to document the backup requirement clearly enough
  that the owner actually keeps one - see `docs/deployment/ANDROID_SIGNING.md`.

### 8. DNS still points to a dead VM

- Not a data-loss scenario. Recovery is provisioning a replacement host (scenario 5) and
  updating the DNS A records to the new IP - both owner-gated actions
  (`PRODUCTION_DNS_CUTOVER_APPROVED`).
- Until DNS is updated, the service is unreachable at its public hostnames even after a
  successful restore elsewhere - document this explicitly to avoid a restored-but-still-down
  situation being mistaken for an unresolved data problem.

## RPO / RTO - test-environment measurements only

**These are measurements taken in a throwaway Docker environment during the Phase 14
drill, not a production SLA.** No contractual guarantee is made or implied. See
`docs/PHASE_14_ENGINEERING_REPORT.md` §M for the exact run this table summarises.

| Measurement | Observed (throwaway drill dataset) |
|---|---|
| Backup creation time | a few seconds, for a dataset on the order of tens of KB |
| Restore time (`pg_restore` + backend startup to healthy) | well under one minute |
| Empty-DB bootstrap (Flyway, 6 migrations) to healthy | a few seconds |

Real production timings depend on real production data volume, disk and network
performance, and have not been measured - they will scale with actual database size in a
way this tiny drill dataset cannot predict.

**RPO** (how much data could be lost) is a direct function of backup frequency, which the
owner has not yet chosen (§AC / §51 of the engineering report - no production schedule is
active). Until a schedule is chosen and enabled, RPO is effectively "however long since the
last manually-run backup" - this is stated honestly rather than assumed to be small.

**RTO** (how long recovery takes) for a real production incident additionally includes
human time: noticing the incident, provisioning a replacement host if needed, and DNS
propagation delay for scenario 5 - none of which the throwaway drill measures.
