# Runnable evaluation environment (V2.0.2)

A complete, isolated V2 stack for **evaluation, not production**: PostgreSQL, the backend, the Public Web behind Caddy,
and evaluation Android builds of both apps, running on the development workstation. It uses **only cleared or fictional
data**. The VPE/GYSEV-derived railway dataset stays `PENDING` and is not used
([EXTERNAL_PERMISSIONS_DEFERRED.md](EXTERNAL_PERMISSIONS_DEFERRED.md)). `v2.0.2` is deployed unmodified.

> **Note (2026-09-21).** This page describes the local evaluation stack only. The live system on the owner's VM is documented in [LIVE_DEPLOYMENT_V2.md](LIVE_DEPLOYMENT_V2.md); the
> SSH situation described in §1 was true when this was written and no longer is.

## 1. Why it runs locally and not on the V1 VM

The workstation holds **no SSH key** for the Oracle VM (`~/.ssh` contains only `known_hosts`), and the runbook has never been
executed ([SERVER_RUNBOOK.md](SERVER_RUNBOOK.md)). A remote deployment could not be performed or verified from here, and V1 must not
be touched. Everything below therefore runs in Docker on this machine, on ports that exist only on `127.0.0.1`.

What can be reused **on the VM** later, unchanged: the backend JAR, the Public Web `dist`, `deploy/caddy/Caddyfile` (three hosts),
`deploy/systemd/orszem-backend.service`, the env template and the runbook. The VM's V1 Caddy container owns 80/443, so V2 there
must be added to that Caddy or wait for V1's retirement ([SERVER_RUNBOOK.md](SERVER_RUNBOOK.md) §0). None of that is done here.

## 2. Layout and isolation

| | |
|---|---|
| Compose project | `orszem-eval` (`deploy/eval/docker-compose.yml`), own network `orszem_eval_net` (172.29.80.0/24), own volume `orszem_eval_pgdata` |
| Containers | `orszem-eval-db` (postgres:16-alpine), `orszem-eval-backend` (eclipse-temurin:21-jre running the tagged JAR), `orszem-eval-caddy` (caddy:2) |
| Published ports | `127.0.0.1:18080` (Caddy: Public Web and `/api/*`), `127.0.0.1:55432` (PostgreSQL, for the CLI and backup drill). The backend publishes nothing |
| Edge policy | Same as production (`deploy/eval/Caddyfile.eval`): same-origin API, actuator/OpenAPI/Swagger never routed, same CSP on the web app. Differences: plain HTTP on loopback, no HSTS |
| Secrets | The database password is generated by `eval.sh init` into `~/.orszem/eval/eval.env` (outside the repository). Nothing secret is committed |
| Cost | none (public images, local machine) |

A failed evaluation is destroyed with `deploy/eval/eval.sh destroy`; nothing else is affected.

## 3. Run it

```bash
# artefacts built from the immutable tag (see §6)
deploy/eval/eval.sh init <backend.jar> <public-web-dist>
deploy/eval/eval.sh up
deploy/eval/eval.sh status                                    # containers + GET /api/v1/meta through Caddy
deploy/eval/eval.sh cli reference-import reference-data/example       # phase A: COMPLETE (inference)
deploy/eval/eval.sh cli create-super-admin                            # prints the one-time credential once
ORSZEM_SEED_ID=SZ-… ORSZEM_SEED_TEMP=… node deploy/eval/seed-eval.mjs # areas, line mappings, users
deploy/eval/eval.sh cli reference-import reference-data/evaluation     # phase B: PARTIAL, adds two settlements and a line
deploy/eval/eval.sh backup && deploy/eval/eval.sh restore-drill
```

Open `http://127.0.0.1:18080/` (Public Web).

## 6. Android evaluation builds

Built from the tag with the **existing** mechanism (`-PORSZEM_API_BASE_URL`), so no application code changed:

```bash
cd android
./gradlew :public-app:assembleDebug :service-app:assembleDebug -PORSZEM_API_BASE_URL=http://10.0.2.2:18080/       # emulator
./gradlew :public-app:assembleDebug :service-app:assembleDebug -PORSZEM_API_BASE_URL=http://127.0.0.1:18080/     # USB device
```

| APK | Base URL | Use |
|---|---|---|
| `orszem-{public,service}-EVAL-2.0.2-emulator.apk` | `http://10.0.2.2:18080/` | Android emulator (10.0.2.2 is the host's loopback) |
| `orszem-{public,service}-EVAL-2.0.2-usb-adb-reverse.apk` | `http://127.0.0.1:18080/` | a physical device over USB after `adb reverse tcp:18080 tcp:18080` |

**They are debug-signed evaluation builds, not production-signed.** Application IDs are `hu.orszembejelento.app.debug` and
`hu.orszembejelento.service.debug`, so they never replace or collide with a production install. The debug network policy permits
cleartext only to `10.0.2.2`, `localhost` and `127.0.0.1`; the release policy stays HTTPS-only. A device on Wi-Fi reaching a LAN
address would need a debug-config change to application code, so it is **not** provided: use USB and `adb reverse`. The production V2
signing key stays an owner-only gate ([ANDROID_SIGNING.md](ANDROID_SIGNING.md)); the V1 key was not used.

## 8. Known limits

- All local clients share one source address (Docker's gateway), so the anonymous submission limit (10, then 1 per 20 s) is shared:
  scripted and manual submissions can throttle each other.
- Single instance, in-memory limiter, plain HTTP: not a production topology. The real HTTPS hostnames need the DNS cutover (owner gate).
- The Service reassign picker lists accounts outside the report's area; the backend refuses them (`400 INVALID_ASSIGNEE`).
- Android was exercised on **one emulator only**, driven by scripted input; no physical device was tested. Once, the Service app raised an
  ANR ("Application does not have a focused window") when scripted taps were sent while the app was still starting after a force-stop; it did
  not recur with proper waits, so it is recorded as a test-driving artefact, not diagnosed further.
- The first Public Android "Frissítés" tap right after a state change can still show the previous status; a second tap shows the new one.
- The Service forced-password-change screen was shown and cancelled (so the owner keeps that account untouched); completing it was only
  exercised through the API.
