# ADR 0008 — the Public reporting backend: identity, credential, idempotency, locking

**Status:** accepted · 2026-09-08

## Context

Phase 4 adds the first thing Őrszem actually exists for: an anonymous citizen can submit a
report. Nothing about who they are is ever collected, so the system needed a way to let that
same anonymous person safely retry a submission and later check its status, without an
account, without a password, and without becoming trivially guessable by anyone else.

## Decision 1 — two identities, one credential

A report has an **internal id** (`reports.id`, used in every FK and join, never returned by
any API) and a **public id** (`reports.public_id`, the only identity a Public client is ever
given). Splitting them means the internal key can be reused freely without ever becoming an
API contract - the same reasoning as `settlements`/`railway_lines` in ADR 0006, applied to
reports.

The public id alone is not a secret - UUIDs are guessable-resistant but not access control.
Access to a specific report's detail is a separate, explicit capability:
**`PublicReportAccessCredential`** - `pr_` followed by 43 URL-safe base64 characters, the
unpadded encoding of 256 CSPRNG-random bits.

**Generated by the client, never by the backend**, before the first submission attempt. The
backend only validates the *shape* and stores `SHA-256(credential)` - never the credential
itself, never a reversible encryption of it, and never a per-deployment HMAC secret that
would let one leaked value compromise every report. A weak credential from a broken or
malicious client compromises only that client's own report, because every report's
credential is independent.

Sent as `X-Orszem-Report-Access` on every request that needs it - the initial `POST`, a
retry of it, and every later `GET` - never a query parameter, path segment, cookie, or
response body. Verified with `MessageDigest.isEqual`, which the JDK documents as
constant-time in the compared lengths, so no hand-rolled constant-time comparison was
needed.

### Why the client generates it

If the response to a successful `POST` is lost after the database commit (a dropped
connection, a client crash), the client still has everything it needs to retry safely: the
`clientSubmissionId` and access credential it already generated *before* sending the first
attempt. The backend never needs an idempotency response cache, and never needs to answer
"what was my credential again?" - a question it could only answer by storing what it must
never store.

**Client contract for Phase 5** (documented now, not built): before the *first* submission
attempt, a client must generate and persist `clientSubmissionId` and the access credential
together, paired with the local history item. Every retry must resend both. After a
successful response, the client persists the returned public report id alongside them. None
of this is implemented in Android or Web during Phase 4.

## Decision 2 — idempotency by normalized comparison, not raw-request hashing

`clientSubmissionId` is the idempotency key, enforced as a database `UNIQUE` index - not an
application-level check-then-insert, which would race. A replay is recognised by comparing
**normalized business fields** (`occurredAt` as an `Instant`, normalized `trainIdentifier`,
`settlementId`, optional `railwayLineId`, `eventTypeCode`) against what is stored, never a
hash of the raw request body. JSON whitespace, property order, and equivalent textual
timestamp representations must not change idempotency semantics, and comparing normalized
fields directly is clearer than inventing a raw-request fingerprint that would need its own
normalization rules anyway. `categoryCode` is deliberately not part of the client payload at
all - the backend derives it from `eventTypeCode` server-side, which removes an entire class
of category/event inconsistency from the API contract.

**Ordering is load-bearing**: a replay is recognised and answered from what is already
stored *before* any business validation runs against today's state. A settlement active on
day 1 and deactivated by day 30 must still let a day-30 retry of a day-1 submission return
the original report - re-validating a replay against current state would incorrectly refuse
a request that already succeeded.

Same `clientSubmissionId`, matching payload and credential → the same report, replayed (HTTP
200). Same `clientSubmissionId`, differing payload or credential → refused
(`IDEMPOTENCY_KEY_REUSED`, HTTP 409) - deliberately one code for both kinds of mismatch, so a
caller cannot use the response to work out which part of a guessed request was "closer".

### Concurrency

`JdbcReportRepository.tryInsert` uses `INSERT ... ON CONFLICT (client_submission_id) DO
NOTHING`. Two concurrent identical submissions: one wins the insert, the other observes the
conflict, re-reads the now-committed winning row (PostgreSQL blocks the losing `INSERT`
until the winner's transaction resolves, then re-evaluates the constraint - no busy-wait, no
extra locking), and returns the identical replay. Two concurrent submissions sharing an id
but disagreeing on payload or credential: exactly one wins; the other, on losing the race,
runs through the exact same replay-or-conflict comparison as the sequential path and gets
409. No JVM `synchronized`, no in-memory mutex, no Redis - the unique index is the only
thing making this true, proved by real concurrent-thread tests against real PostgreSQL.

## Decision 3 — the reference-state lock, reused as a shared/exclusive pair

A report submission reads reference/service-area state (settlement, railway line, and
everything `RoutingService` reads) and must not do so in the middle of a reference import
changing what is current. Rather than inventing a second lock, this reuses
`ReferenceStateLock`'s single key (ADR 0007) both ways:

- a reference import holds it **exclusively** (`pg_advisory_xact_lock`, unchanged from
  Phase 3B/3C);
- a report submission holds it **shared** (`pg_advisory_xact_lock_shared`, new in this
  phase) for the whole transaction, from just before the first reference-data read through
  routing and the insert.

Many submissions may hold the shared lock concurrently - ordinary traffic never contends
with itself. An import waits for every in-flight submission to finish before it can start
changing anything; a submission that begins while an import is in flight waits for the
import to finish first. Either way, everything one submission's transaction reads - the
settlement, the optional railway line, and every query `RoutingService` makes - is
guaranteed to reflect one consistent reference-state revision, never a version where some
reads saw the old state and others saw the new one mid-import.

The key is centralised in one object (`common/ReferenceStateLock`) specifically so the
exclusive and shared call sites can never drift onto different values by accident - the
whole safety property depends on them being the *same* key.

## Decision 4 — routing failure is not report failure

Once `settlementId`, the optional `railwayLineId`, and `eventTypeCode` are validated to
exist (and, for settlement/event type, to be active), and a current reference state exists
to route against, **every** `RoutingService` outcome results in a successfully created
report - `Routed` and all six `Unclassified` reasons alike, `REFERENCE_MISMATCH` included.
`REFERENCE_MISMATCH` in particular is *not* treated as invalid input: a known railway line
with no verified relation to the settlement, under `PARTIAL` relation coverage, is not proof
the reporter is wrong - it is proof only that the dataset has not (yet) verified that
relation (ADR 0006). Refusing the report on that basis would silently discard a genuine
safety report because of a data-completeness gap, which is precisely what `PARTIAL`
coverage exists to avoid asserting.

Only three conditions refuse the request entirely, before a report is ever created:
`INVALID_SETTLEMENT`/`INVALID_EVENT_TYPE`/`INVALID_RAILWAY_LINE` (the identity itself does
not resolve, or - for settlement/event type - is not active), and
`REFERENCE_DATASET_UNAVAILABLE` (no current reference state exists to route against at
all - infrastructure, not a business classification, exactly as ADR 0007 already
distinguishes for `RoutingService.route`'s own return type).

`RoutingOutcome.Unclassified` gained one additive field for this phase,
`resolvedRailwayLineId: UUID? = null`, defaulted so no Phase 3 call site changed behaviour:
present exactly when a line *was* resolved (by inference or explicit selection) and only
then found unassigned, inactive, or its area inactive; null for the reasons reached before
any line was resolved at all. `report_routing_snapshots` needed this distinction to satisfy
its own coherence constraint (below); `RoutingService`'s decision logic is unchanged.

## Decision 5 — the routing snapshot is current state, not history

`report_routing_snapshots` is a one-to-one table holding the routing decision **as it
currently stands** - not event sourcing. A later phase that deliberately re-routes a `NEW`
report overwrites this row; nothing records what the value was before. Historical/audit
concerns for routing changes are a separate, later decision, not built here.

Coherence is a database `CHECK` constraint, not application discipline: `ROUTED` always
names a service area and a resolved line and carries no reason; `UNCLASSIFIED` always
carries a reason and never a service area (its resolved line is unconstrained, matching
Decision 4's distinction above).

`reference_dataset_version` carries forward ADR 0007 Decision 2's meaning unchanged: it
names the reference-state revision that was current when the snapshot was computed, not
that every fact used in the decision originated in that specific import. A relation
preserved from an older `PARTIAL` import (ADR 0006) can still be exactly what resolved a
report, reported under the newest version's label.

## Decision 6 — the Public status vocabulary is not the internal one

Internal: `NEW → IN_PROGRESS → ARCHIVED`. Public: `RECEIVED → PROCESSING → CLOSED`. `NEW` is
never sent to a Public client, by name or by any distinguishable behaviour. A future
moderation-deleted report (not built yet) will also map to `CLOSED`, not a new public value
- moderation state is an internal workflow concern the Public API was never going to expose
either way.

## Decision 7 — no audit row for anonymous submission

`audit_events` (Phase 2) exists for security-sensitive identity/session events - who
authenticated, whose password changed, whose session was revoked. An anonymous report has
no actor to attribute it to, and the report row itself is already the authoritative record
of its own creation; writing a second, high-volume copy into the security audit trail for
every submission would blur what that trail is for without adding information. No
`REPORT_CREATED` audit event and no `PUBLIC` actor type were added. Technical logging
(a correlation id, the routing outcome category, a validation error code - never a report
detail beyond what is operationally necessary) is what Phase 4 relies on instead. Staff
workflow mutations, once they exist, are a different question and may reasonably be audited
when they are built.

## Decision 8 — rate limiting is explicitly deferred

`LoginRateLimiter` (Phase 2) is coupled to `AuthProperties` and to service-ID/IP dual-bucket
semantics built for credential-guessing defence. Reusing it for anonymous report submission
would mean touching auth semantics or inventing a materially different, unjustified
threshold for an unrelated traffic shape - exactly what the phase brief asked not to do.
**No anti-abuse rate limiting exists for Public report submission in Phase 4.** This is a
known, explicitly accepted limitation, not an oversight - see `PHASE_4_ENGINEERING_REPORT.md`
and `DECISIONS_REQUIRING_OWNER.md`. Phase 4 is not deployed publicly.

## Consequences

- `RoutingOutcome.Unclassified` carries one new, defaulted field (Decision 4). Every other
  Phase 3 type and behaviour is unchanged.
- `ReferenceStateLock`'s key is now held two ways (exclusive/shared) by two different
  subsystems. A future third user of "read consistent reference state" should take the
  shared lock the same way `SubmitReportUseCase` does, not invent a new key.
- The event taxonomy (`report_categories`/`report_event_types`) is deliberately outside the
  ADR 0006 reference-data lifecycle: it is small, product-controlled, and changes through
  reviewed migrations only, never a runtime importer - see V003's own header comment.
- No retention policy, no report deletion, and no credential expiry exist yet. The access
  credential remains valid for as long as the report exists. This is a deliberate
  non-decision, not an implementation gap - see `DECISIONS_REQUIRING_OWNER.md` B5.
